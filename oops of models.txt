 __str__ — what does my object look like as a string?                                                                                         
                                                                                                                                               
  This is a Python thing, not a Django thing. Every Python object can define a __str__ method that controls how it shows up when something     
  needs to display it as text.                                                                                                                 
                  
  Without __str__, Python's default is ugly:

  cat = Category(name="Django")
  print(cat)
  # → <Category: Category object (1)>     ← useless

  With your __str__:

  def __str__(self):
      return self.name

  print(cat)
  # → Django                              ← readable

  Where it actually shows up in Django:
  - The admin panel — the dropdowns, the lists, the breadcrumbs. Without __str__, akash logs into the admin and sees a list of "Category object
   (1)", "Category object (2)" — useless. With it, he sees "Django", "PostgreSQL", "DevOps".
  - The Django shell — when you print(category), you see "Django" instead of the gibberish.
  - Anywhere Django auto-renders a model object as text in a template.

  About the funny __ syntax — those double underscores are called "dunders" (short for "double underscore"). It's a Python naming convention
  for magic methods — methods Python and frameworks call automatically behind the scenes. You don't call __str__() yourself — Django calls it
  when it needs a string. Other dunders you'll meet: __init__ (called when you create an object), __len__ (called by len()), __add__ (called by
   +).

  Thumb rule: every model you write should have a __str__. It costs three lines and saves you from gibberish in the admin forever.

  class Bank:                                               
      def __init__(self, name, ifsc):
          self.name = name
          self.ifsc = ifsc

  sbi   = Bank("SBI",   "SBI0001")
  icici = Bank("ICICI", "ICIC0001")
  hdfc  = Bank("HDFC",  "HDFC0001")

  What you just wrote:

  class Category(models.Model):
      name = models.CharField(max_length=100, unique=True)
      slug = models.SlugField(unique=True)

  # Later, somewhere else in the code:
  django   = Category(name="Django",     slug="django")
  postgres = Category(name="PostgreSQL", slug="postgresql")
  devops   = Category(name="DevOps",     slug="devops")

  The big picture is identical: a class is the blueprint, instances are the actual things. Category is the blueprint; django, postgres, devops
  are three instances of that blueprint — same way sbi, icici, hdfc are three instances of Bank.

  But there are five things that look different. Each one has a reason.

  ---
  Difference 1 — (models.Model)

  class Bank:                       # plain Python class
  class Category(models.Model):     # inherits from Django's Model class

  The (models.Model) is inheritance — Category is-a Model. By inheriting, your class gets Django's database machinery for free: the ability to
  save rows, query rows, run migrations, etc. Without it, you'd just have a plain Python class with no connection to any database.

  Same idea as if you wrote class SavingsBank(Bank): — you'd get all of Bank's features plus add your own.

  ---
  Difference 2 — fields are declared at the class level, not in __init__

  In your Bank class, attributes get set inside __init__:

  class Bank:
      def __init__(self, name, ifsc):
          self.name = name        # ← assignment happens at instance creation time
          self.ifsc = ifsc

  In your Category model, they're declared right inside the class body:

  class Category(models.Model):
      name = models.CharField(...)    # ← declared at the CLASS level
      slug = models.SlugField(...)

  Why the difference? Django needs to know the table's column structure before any instance ever exists — to generate migrations, build the SQL
   CREATE TABLE, etc. So Django scans the class itself (not any instance) for these field declarations.

  You don't write __init__ for a Django model. Django auto-generates one for you that accepts your field names as keyword arguments. That's why
   Category(name="Django", slug="django") Just Works — Django wrote that __init__ behind the scenes.

  ---
  Difference 3 — models.CharField(...) isn't a value, it's a column description

  self.name = "SBI"                          # ← "SBI" is just a string value
  name = models.CharField(max_length=100)    # ← this is a Field object describing a column

  When you write models.CharField(max_length=100, unique=True), you're not storing a string. You're creating a CharField object that tells
  Django "this column should be a varchar(100), it must be unique."

  When you later do django.name = "Django", Django swaps in the actual string. The CharField is the schema — the rule for what can go in that
  slot. The string is the value.

  Think of it like this:
  - CharField(max_length=100) is the column definition ("this column holds short text")
  - "Django" is the value sitting in one row of that column

  ---
  Difference 4 — creating an instance looks the same

  sbi = Bank(name="SBI", ifsc="SBI0001")
  django = Category(name="Django", slug="django")

  Identical syntax. Class name, parentheses, keyword arguments. Both produce one instance of the class. Your existing intuition transfers 100%.

  ---
  Difference 5 — the new bit you haven't seen yet: .save()

  This is the one new thing.

  sbi = Bank("SBI", "SBI0001")
  # That's it. The object lives in memory. Done.

  django = Category(name="Django", slug="django")
  # Object lives in memory. NOT in the database yet.
  django.save()
  # NOW it's a row in the database.

  A Django model instance has two states:
  1. In memory only — you've created the Python object but the database has no idea it exists.
  2. Saved to the database — there's now an actual row in PostgreSQL.

  .save() is the bridge. It's the moment Python writes a row into the table.

  ---
  Map back to what you wrote

  class Category(models.Model):                                # blueprint
      name = models.CharField(max_length=100, unique=True)    # column 1
      slug = models.SlugField(unique=True)                    # column 2

      def __str__(self):                                       # instance method
          return self.name                                     #   self = "this specific row"

      class Meta:                                              # config about the table itself
          verbose_name_plural = 'categories'

  In def __str__(self), the self is exactly the same self from your Bank class — "the specific instance this method is being called on." When
  Django prints django.name, it's calling __str__ on that specific Category instance, and self.name returns "Django".

  So the OOP picture is the picture. Django models are just regular Python classes with extra batteries — inheritance from Model to get DB
  powers, fields declared at class-level so Django can introspect the schema, and a .save() method to persist instances as rows.

   Good question — and the answer is no, they're different things. Let me untangle this clearly because both are dunders, so the confusion is   
  fair.                                  
                                                                                                                                               
  Two different magic methods, two different jobs
                                                                                                                                               
  ┌──────────┬──────────────────────────────────────────────────────────┬──────────────────────────────────────────┐
  │  Dunder  │                       When it runs                       │               What it does               │
  ├──────────┼──────────────────────────────────────────────────────────┼──────────────────────────────────────────┤
  │ __init__ │ Once — when you create a new instance                    │ Builds the object (sets self.name, etc.) │
  ├──────────┼──────────────────────────────────────────────────────────┼──────────────────────────────────────────┤
  │ __str__  │ Every time something needs to display the object as text │ Returns the string representation        │
  └──────────┴──────────────────────────────────────────────────────────┴──────────────────────────────────────────┘

  So they fire at totally different moments and do totally different jobs.

  ---
  Your Bank class with both dunders made explicit

  class Bank:
      def __init__(self, name, ifsc):     # CONSTRUCTOR — builds the object
          self.name = name
          self.ifsc = ifsc

      def __str__(self):                   # STRING REPRESENTATION — describes the object
          return self.name


  sbi = Bank("SBI", "SBI0001")    # ← __init__ fires here. Object is built in memory.
  print(sbi)                       # ← __str__ fires here. Output: "SBI"
  str(sbi)                         # ← __str__ fires again. Returns "SBI"

  sbi = Bank(...) is the creation moment — that triggers __init__.
  print(sbi) is the display moment — that triggers __str__.

  If you removed __str__, sbi = Bank(...) would still work fine. You'd just get ugly output like <__main__.Bank object at 0x7f...> when you
  tried to print it.

  ---
  Same picture for your Category

  class Category(models.Model):
      name = models.CharField(max_length=100, unique=True)
      slug = models.SlugField(unique=True)

      # __init__ exists too — Django auto-generates it. You don't write it.

      def __str__(self):
          return self.name


  django = Category(name="Django", slug="django")  # ← Django's auto-__init__ fires
  print(django)                                     # ← __str__ fires. Output: "Django"

  So:

  - Creating an instance (sbi = Bank(), django = Category()) — that's __init__ at work. In Django's case, you don't write __init__ — Django
  writes it for you, but it still runs.
  - Printing/displaying an instance — that's __str__ at work. You write __str__ yourself in both Python and Django.

  ---
  The key insight

  sbi = Bank(...) and __str__ aren't the same thing.

  - sbi = Bank(...) is the action of creating an instance. The dunder behind it is __init__.
  - __str__ is a method that decides what the instance looks like as a string when someone later prints it.

  Two separate moments in the life of an object: birth (__init__) and display (__str__).

  ---
  So why does print(sbi) work at all without __str__?

  Because every Python object inherits a default __str__ from the base object class. That default __str__ returns <ClassName object at
  0xMEMORY_ADDRESS>. That's why your code never errored — Python always has something to print, just nothing useful.

  When you write your own __str__, you're overriding the ugly default with something meaningful. Same as overriding any inherited method.

  ---
  Why this matters in Django specifically

  The Django admin, the shell, error messages, log output — all of these end up calling str(category) somewhere internally. Without __str__,
  akash logs into the admin and sees a list like:

  Category object (1)
  Category object (2)
  Category object (3)

  Useless. With __str__ returning self.name, he sees:

  Django
  PostgreSQL
  DevOps

  Same code runs either way. Same number of clicks. The difference is whether the human looking at the screen can do their job.

  So the rule of thumb: every Django model gets a __str__. Three lines, costs you nothing, saves you from gibberish forever.
