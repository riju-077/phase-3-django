  You're right — ORM is a big advantage. But it's not the only one.
                                          
  What you saw at your internship is the DB-driver-direct approach:                                                                            
                                                                                                                                               
  import pyodbc                                                                                                                                
                                                                                                                                               
  conn = pyodbc.connect('Server=...;Database=...;')         
  cursor = conn.cursor()
  cursor.execute("SELECT * FROM Users WHERE id = ?", (user_id,))
  row = cursor.fetchone()
  user_name = row[0]
  user_email = row[1]

  Versus the same thing through Django's ORM:

  user = User.objects.get(id=user_id)
  user_name = user.username
  user_email = user.email

  Same outcome. Django translates the Python code into the equivalent SQL behind the scenes, opens the connection, runs the query, parses
  results into Python objects, and hands you back a typed object. That part you observed correctly — it's a big deal.

  What you likely saw at your internship: probably one of these — a data pipeline, an internal report tool, or a team that just preferred SQL.
  It's not "wrong" — it's a different tool fit.

  ---
  When frameworks really earn their keep

  Django (or FastAPI, Rails, Laravel, etc.) starts paying off the moment you have any of these requirements:

  - Users that need to log in
  - Forms that need validation
  - A web UI that's more than 5 pages
  - An admin who needs to manage data
  - An API that more than one client consumes
  - Multiple developers working together (consistent structure)
  - Schema that'll evolve over months/years (migrations are gold)
  - Security defaults you don't want to think about

  Once your app has 2+ of those, the framework saves orders of magnitude of code and bugs.

  ---
  A working mental model

  Think of it as a spectrum:

  Raw SQL + driver    Mini-frameworks    Full frameworks
  (pyodbc, psycopg2)  (FastAPI, Flask)   (Django, Rails)

     most control            ←→            most batteries
     most code to write                    fastest to start
     thin layer                            heavy layer

  You pick where on this spectrum to sit based on the job.

  - Raw SQL — scripts, data pipelines, analytics, ETL
  - Mini-frameworks — small APIs, microservices, ML model serving
  - Full frameworks — anything with users, multiple pages, admin, evolving schema

  Phase 3 of your project sits firmly in the full framework zone — you've got users, posts, an admin, an API, search, races. Django is paying
  for itself heavily here.

  ---                                                                                                                                          
  SQL injection — it's about where the input comes from, not raw vs ORM
                                                                                                                                               
  The injection risk isn't really "raw SQL is dangerous, ORM is safe." It's:                                                                   
                                                                                                                                               
  ▎ "Are you concatenating untrusted input into a query string?"                                                                               
                                                            
  If you write this:
  cursor.execute(f"SELECT * FROM Users WHERE id = {user_input}")   # 💀 injection risk

  You're vulnerable. Doesn't matter that it's raw SQL — the bug is the f-string concatenation.

  If you write this:
  cursor.execute("SELECT * FROM Users WHERE id = ?", (user_input,))   # ✅ safe

  You're safe. The ? is a placeholder; the driver sends the parameter separately and the database knows it's data, not code. This is
  "parameterized queries" — and every SQL driver in every language supports it.

  What Django ORM gives you is parameterization by default — you can't easily not parameterize, even by accident. With raw SQL, you have to
  remember to do it. So:

  ┌───────────────────────────────┬────────────────────────┬───────────────────────┐
  │ Raw SQL with parameterization │ Raw SQL with f-strings │      Django ORM       │
  ├───────────────────────────────┼────────────────────────┼───────────────────────┤
  │ ✅ Safe                       │ 💀 Vulnerable          │ ✅ Safe automatically │
  └───────────────────────────────┴────────────────────────┴───────────────────────┘

  ---
  Your internship's specific context — RL for Amazon RTB

  This is exactly the use case where raw SQL is the right call. A few reasons it tracks:

  1. No untrusted input. RL training scripts pull from internal data warehouses. The "input" is a config file, a date range, an experiment id —
   written by the data team, not a public form. Even with f-string concatenation (which they shouldn't do, but is less catastrophic), the
  threat model is "an internal engineer typing weird strings" — much smaller blast radius than "the entire internet."
  2. Read-heavy, complex queries. RL/ML pipelines often need analytics-shaped queries: window functions, multi-joins, aggregations across
  billions of rows. ORMs can express these, but the raw SQL is usually cleaner and lets the data engineer hand-tune execution plans (EXPLAIN,
  hints, indexed columns). When you're optimizing a query that runs over Amazon's ad-stream-scale data, every millisecond matters.
  3. No web app machinery needed. They don't need URL routing, auth, forms, admin, sessions, or templates. A whole framework would just be
  weight. The script does one thing — read data, train a model, output bids/predictions. Pandas + pyodbc covers it.
  4. Pipeline lives behind firewalls. It runs as a job (Airflow, cron, internal scheduler), not as a public service. Even if a vulnerability
  existed, an attacker would need internal network access, internal credentials, and a path through orchestration. The threat surface is tiny.

  So the team's call is defensible — even if they're concatenating in places. Different threat model = different rules.

  ---
  When their setup would become genuinely dangerous

  The moment any of these change, the calculus flips:

  - They build a dashboard where a non-technical PM can run "ad-hoc queries" by pasting filters → injection risk reappears.
  - They expose the model behind a public REST endpoint where users send query parameters → must sanitize / parameterize.
  - They share the codebase with junior engineers without explicit guidance → someone will concatenate input eventually.
  - Compliance auditors come knocking and demand defense-in-depth → "but it's internal" stops being a sufficient answer.

  At that point, either retrofit parameterization or wrap a thin framework around it. Most production teams settle on a hybrid: framework for
  anything user-facing, raw SQL for internal pipelines.

  ---
  Engineering judgment, distilled

  You've actually identified the mature view in two paragraphs of your own observation:

  ▎ "They didn't make it public, was only using for themselves."

  That's exactly the question every senior engineer asks: what's the threat model? If the answer is "internal team, no public access, known
  inputs" — you can drop a lot of the defensive armor. If the answer is "anyone on the internet can hit this" — armor up, hard.

  Frameworks give you sensible armor by default. Raw SQL forces you to put the armor on yourself. Both can produce safe code. Both can produce
  unsafe code. The deciding factor is who can talk to your code, and what can they say to it.
