 What a foreign key actually is                                                                                                               
                                                                                                                                               
  Forget Django syntax for a second. Just look at the database.                                                                                
                                                                                                                                               
  Your posts table will have columns. One of them is author. What does the database physically store in that column for each row? Not the whole
   user object. Not the username. Just an integer — the id of a row in the User table.

  Here's what it looks like on disk:

  auth_user table (Django's built-in users):

  ┌─────┬──────────┬───────────┐
  │ id  │ username │   email   │
  ├─────┼──────────┼───────────┤
  │ 1   │ admin    │ admin@... │
  ├─────┼──────────┼───────────┤
  │ 5   │ akash    │ a@...     │
  ├─────┼──────────┼───────────┤
  │ 7   │ priya    │ p@...     │
  └─────┴──────────┴───────────┘

  posts_post table (yours):

  ┌─────┬───────────────┬──────┬───────────┐
  │ id  │     title     │ body │ author_id │
  ├─────┼───────────────┼──────┼───────────┤
  │ 1   │ "First post"  │ ...  │ 5         │
  ├─────┼───────────────┼──────┼───────────┤
  │ 2   │ "Second post" │ ...  │ 5         │
  ├─────┼───────────────┼──────┼───────────┤
  │ 3   │ "Hello"       │ ...  │ 7         │
  └─────┴───────────────┴──────┴───────────┘

  The author_id = 5 literally means "this post is written by the user whose id is 5." That's it. A foreign key is just a number stored in your
  row that points at another row in another table.

  When in your Python code you write post.author.username, Django sees the author_id, runs a SQL JOIN under the hood — "give me the user where
  id = 5" — and hands you the user object. The "magic" is just follow the pointer, look up the row.

  This is the same idea as a pointer in C or a reference in Java — a tiny, cheap value that says "the real thing lives over there."

  ▎ Naming detail: you write author = ForeignKey(User, ...) in Python. Django stores it in the database as a column called author_id 
  ▎ (auto-appends _id). When you access it in Python, you say post.author (the User object); when you query the raw column, it's author_id.

  ---
  The new import

  User isn't built into your code — it's Django's built-in user model living at django.contrib.auth.models.User. (That auth_user table you saw
  in pgAdmin is exactly this model.) So at the top of models.py, add:

  from django.contrib.auth.models import User

  Right under your existing from django.db import models line.

  ---
  The author field

  Inside your Post class, after body, add:

  author = models.ForeignKey(User, on_delete=models.CASCADE)

  Read it left to right:

  - models.ForeignKey — this column is a foreign key. It stores the id of a row in another table.
  - User — the table it points at. Could be any model class.
  - on_delete=models.CASCADE — the rule we picked together: when a user is deleted, cascade the deletion to their posts. (Same CASCADE we
  discussed in the YouTube channel-deleted story.)

  Why you might have thought it was just id + username

  Two reasons it feels that way:

  1. Most code only uses a couple of fields. Day to day, you mostly access user.username and user.id. The other fields exist but you don't

  2. In tutorials and examples, people show abbreviated tables — exactly like I did. Whenever you see a 2-column or 3-column user table in an
  article, assume the full thing is bigger.
