  Story — the Sunday cleanup script                                                                                                            
                                                                                                                                               
  You're running QuoraClone. It's been live for a year. The posts_post table now has 800,000 draft posts — articles people started but never   
  finished. They've been sitting there for months, never published, never edited again. They're eating database space and slowing down backups.
                                                                                                                                               
  The product manager says: "Auto-delete any draft that hasn't been touched in 6 months. Run it every Sunday night."

  How would you build this without management commands? Three flawed options:

  1. A bash script with raw SQL — fragile, no model validation, easy to delete the wrong rows.
  2. A view function triggered by a button — a developer would have to manually click it every Sunday. Forgettable, error-prone.
  3. A shell session every Sunday night — open shell, paste the cleanup snippet, run it, exit. Imagine doing that for the next 5 years.

  None scale. None are reproducible. None get logged.

  ---
  With a management command

  You write one Python file that defines a custom manage.py subcommand. Once written, you can:
  - Run it manually: python manage.py cleanup_drafts
  - Or schedule it with cron: every Sunday at 2am, run the command, no human involved
  - Or trigger it from CI / an orchestration tool like Airflow

  The file looks something like:

  # posts/management/commands/cleanup_drafts.py
  from django.core.management.base import BaseCommand
  from django.utils import timezone
  from datetime import timedelta
  from posts.models import Post

  class Command(BaseCommand):
      help = "Deletes drafts not touched in 6 months"

      def handle(self, *args, **options):
          cutoff = timezone.now() - timedelta(days=180)
          old_drafts = Post.objects.filter(published=False, updated_at__lt=cutoff)
          count = old_drafts.count()
          old_drafts.delete()
          self.stdout.write(f"Deleted {count} old drafts.")

  Now you run:
  python manage.py cleanup_drafts

  And it prints something like Deleted 47,891 old drafts.

  Schedule it once on a server (cron, Celery beat, AWS EventBridge — whatever your stack uses). It runs forever. You never think about it
  again.

  ---
  What end users feel

  The reader on QuoraClone never sees the cleanup happen. They just experience:
  - Faster page loads (less data to scan)
  - Faster search (smaller search vector index)
  - Lower hosting bills (you, not the reader, but it matters)

  The cleanup is invisible, but the absence of stale data is felt as a smoother site.

  ---
  Groups — what are these?

  This is Django's role-based permissions system. A group is a named bundle of permissions you can attach to multiple users at once.

  The story — a magazine with many writers

  You're running a blog magazine with three kinds of contributors:

  ┌───────────┬───────────────────────────────────────────────────────────────────┐
  │   Role    │                    What they're allowed to do                     │
  ├───────────┼───────────────────────────────────────────────────────────────────┤
  │ Editor    │ Edit any post, delete posts, publish/unpublish                    │
  ├───────────┼───────────────────────────────────────────────────────────────────┤
  │ Writer    │ Create posts, edit their own, cannot publish (an editor approves) │
  ├───────────┼───────────────────────────────────────────────────────────────────┤
  │ Moderator │ Hide posts, ban users, can't edit content                         │
  └───────────┴───────────────────────────────────────────────────────────────────┘

  You hire 15 writers, 3 editors, 2 moderators. Twenty users, each needing the right access.

  Without groups — the painful way

  For each of 20 users, click through the permissions list (Django ships with auto-generated permissions per model: add_post, change_post,
  delete_post, view_post, plus the same for Category, etc.). Tick the right boxes for that role. Save.

  Now hire two more writers. Repeat the same set of clicks. Forget one box, that writer is silently broken.

  Some writer needs editor access temporarily? Manually edit their permissions, then manually undo later. Easy to mess up. No audit trail. Hard
   to keep consistent across the team.

  With groups — the clean way

  You create three groups:

  - Editors — assign these 6 permissions
  - Writers — assign these 3 permissions
  - Moderators — assign these 4 permissions

  Then for each user, just assign them to the right group(s):

  - akash → superuser (gets everything by default)
  - priya → Editors
  - ravi → Writers
  - maya → Moderators

  Hire a new writer? Add them to the "Writers" group. Done. They inherit all writer permissions automatically.

  Permissions for the role change? Edit the group once, every member is updated.

  Need to promote ravi from writer to editor? Move him from "Writers" to "Editors" group. Done.

  This is the same pattern as Linux groups, AWS IAM roles, GitHub teams. Once you know it, you see it everywhere.

  ---
  Why you see it in the admin even though you didn't add it

  Two things to register in the admin:

  admin.site.register(Post)        # ← your code
  admin.site.register(Category)    # ← your code

  You wrote those. But Django also auto-registers User and Group because django.contrib.auth ships with its own admin code that registers them.
   Same as how django.contrib.admin ships the admin panel itself. Apps can register their own admin views.

  If you opened posts/admin.py and removed your two register() lines, "Categories" and "Posts" would disappear from the admin sidebar — but
  "Users" and "Groups" would still be there, because auth registered them.

  ---
  You'll touch Groups when?

  For your blog learning project — probably never. With one author (akash), you don't need groups.

  In production / multi-author apps — constantly. Groups are how you scale permissions without going insane. The moment your app has more than
  ~5 users with different access levels, groups become essential.

  DRF also has its own permissions system (which we'll meet in concept #12) that builds on top of Django's auth groups. So your API endpoints
  can say things like "this endpoint requires the user to be in the Editors group."
