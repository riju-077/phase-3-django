  ---                                                                                                                                          
  What middleware actually is                                                                                                                  
                                                                                                                                               
  Every HTTP request that comes into your Django app passes through a stack of middleware before reaching your view. Then the response passes  
  back through the stack on the way out.                                                                                                       
                                                                                                                                               
  Picture it like this:                                     

  Browser sends request
         ↓
     Middleware 1 (security headers)
         ↓
     Middleware 2 (sessions)
         ↓
     Middleware 3 (auth)
         ↓
     Middleware 4 (CSRF)
         ↓
     Your view runs ──── queries DB, builds response
         ↓
     Middleware 4 (CSRF)  ← response on the way back out
         ↓
     Middleware 3 (auth)
         ↓
     Middleware 2 (sessions)
         ↓
     Middleware 1 (security headers)
         ↓
  Browser receives response

  Each middleware can inspect and modify the request on the way in, and inspect and modify the response on the way out.

  You've already been using ~7 middleware all along — they're listed in blog/settings.py under MIDDLEWARE = [...]. They handle security,
  sessions, auth, CSRF, etc. Now you write your own.

  ---
  What we'll build — a request logger

  Goal: every time anyone hits any URL, your dev server's terminal prints a line like:

  GET /api/posts/ → 200 (0.012s)
  GET /api/posts/5/ → 200 (0.008s)
  GET /api/categories/ → 200 (0.024s)
  GET /api/posts/9999/ → 404 (0.005s)

  Useful for:
  - Spotting slow endpoints during development
  - Tracking which endpoints get hit most
  - Debugging — "did my request even reach the server?"

  In production, real apps use logging libraries (Python's logging module + log shippers like Loggly/Datadog) — but the concept is identical.
  You're just observing every request flow through.

  ---
  Step 1 — create blog/middleware.py

  A new file. Put it inside the blog/ project folder (next to settings.py, urls.py).

  Type:

  import time


  class RequestLoggingMiddleware:
      def __init__(self, get_response):
          self.get_response = get_response
          # __init__ runs ONCE when the server starts

      def __call__(self, request):
          # __call__ runs on EVERY request
          start = time.time()

          response = self.get_response(request)

          duration = time.time() - start
          print(f"{request.method} {request.path} → {response.status_code} ({duration:.3f}s)")

          return response

  ---
  What each piece does

  __init__(self, get_response) — runs once when the server starts. Django hands you get_response, which is a function representing the rest of
  the middleware chain plus your view. Save it for later.

  __call__(self, request) — runs on every request. The dunder __call__ is what makes an instance callable — Django effectively does
  middleware(request) for every incoming request. Same magic method as __str__/__init__.

  Inside __call__:
  1. Code before self.get_response(request) runs before the view. (Here: capture start time.)
  2. self.get_response(request) dispatches to the next middleware / your view, gets back a response.
  3. Code after runs after the view returns. (Here: compute duration, print log line.)
  4. You must return the response — Django ships it back to the client.

  The structure is essentially: "Wrap the view in before/after hooks." If you're familiar with Python decorators, middleware is functionally
  similar — wrapping a function with extra behavior.

  ---
  Step 2 — register it in blog/settings.py

  Find the existing MIDDLEWARE = [...] list (probably 6-7 entries already). Add your middleware to the bottom:

  MIDDLEWARE = [
      'django.middleware.security.SecurityMiddleware',
      'django.contrib.sessions.middleware.SessionMiddleware',
      'django.middleware.common.CommonMiddleware',
      'django.middleware.csrf.CsrfViewMiddleware',
      'django.contrib.auth.middleware.AuthenticationMiddleware',
      'django.contrib.messages.middleware.MessageMiddleware',
      'django.middleware.clickjacking.XFrameOptionsMiddleware',
      'blog.middleware.RequestLoggingMiddleware',          # ← add this
  ]

  Note the import path: blog.middleware.RequestLoggingMiddleware — that's "the RequestLoggingMiddleware class inside blog/middleware.py."

  Order in this list matters:
  - The list runs top-to-bottom on the way in (request)
  - And bottom-to-top on the way out (response)

  Putting yours at the bottom means it runs closest to the view on the way in and first on the way out (so it captures the duration of the
  actual view + every middleware above it).

  ---
  What's powerful about this

  The middleware ran on every request without you touching any view. You wrote it once, registered it once, and now it observes the entire
  app's traffic.

  Same pattern is used for:
  - Adding authentication checks globally
  - Setting CORS headers
  - Throttling/rate-limiting requests
  - Tagging requests with a unique ID for tracing
  - Maintenance mode ("site is down, come back at 5pm")
  - Logging to external services

  In real apps, libraries like django-cors-headers and django-debug-toolbar are entirely middleware. They drop into MIDDLEWARE and start
  observing/modifying every request.

  # Real middleware would do this:                          
  from loguru import logger

  class RequestLoggingMiddleware:
      def __call__(self, request):
          start = time.time()
          response = self.get_response(request)
          duration = time.time() - start
          logger.info(f"{request.method} {request.path} → {response.status_code} ({duration:.3f}s)")
          return response

  So loguru and middleware aren't competing. Middleware is the where (the request/response pipeline). Loguru is the how (the actual log
  formatting, file rotation, log levels, etc.). A real request-logging middleware would call loguru. They work together.

  ---
  But middleware does WAY more than logging

  Logging is maybe 10% of what middleware is used for. Here are real-world examples that have nothing to do with logging:

  ┌─────────────────────┬───────────────────────────────────────────────────────────────────┬──────────────────────────────────────────────┐
  │     Middleware      │                           What it does                            │      Why you can't write this in a view      │
  ├─────────────────────┼───────────────────────────────────────────────────────────────────┼──────────────────────────────────────────────┤
  │ Maintenance mode    │ When MAINTENANCE_MODE = True in settings, every request returns   │ Has to short-circuit BEFORE any view.        │
  │                     │ "Site down, back at 5pm." The view never runs.                    │ Putting it in views = repeating it 50 times. │
  ├─────────────────────┼───────────────────────────────────────────────────────────────────┼──────────────────────────────────────────────┤
  │ Authentication      │ Verify a JWT token on every API request, attach the user to       │ Has to run before every view, even ones the  │
  │ enforcement         │ request.user.                                                     │ dev forgot to protect.                       │
  ├─────────────────────┼───────────────────────────────────────────────────────────────────┼──────────────────────────────────────────────┤
  │ Rate limiting       │ Track how many requests an IP has made in the last minute. Block  │ Needs to count globally, not per-view.       │
  │                     │ if over 100/min.                                                  │                                              │
  ├─────────────────────┼───────────────────────────────────────────────────────────────────┼──────────────────────────────────────────────┤
  │ CORS headers        │ Add Access-Control-Allow-Origin: * to every response so React     │ Same header on every response — no point     │
  │                     │ frontends on different domains can call your API.                 │ repeating in each view.                      │
  ├─────────────────────┼───────────────────────────────────────────────────────────────────┼──────────────────────────────────────────────┤
  │ Request tracing     │ Attach a unique ID to every request so you can correlate logs     │ Has to happen before the view sees the       │
  │                     │ across microservices.                                             │ request.                                     │
  ├─────────────────────┼───────────────────────────────────────────────────────────────────┼──────────────────────────────────────────────┤
  │ Compression         │ Gzip every response over 1KB.                                     │ Operates on every response uniformly.        │
  ├─────────────────────┼───────────────────────────────────────────────────────────────────┼──────────────────────────────────────────────┤
  │ A/B testing         │ Assign each user to test bucket A or B based on their cookie.     │ Global decision affecting every request.     │
  ├─────────────────────┼───────────────────────────────────────────────────────────────────┼──────────────────────────────────────────────┤
  │ Localization        │ Detect Accept-Language header → set request.LANGUAGE_CODE so      │ Has to run before view for views to use it.  │

  └─────────────────────┴───────────────────────────────────────────────────────────────────┴──────────────────────────────────────────────┘

  The pattern is always the same: something that needs to happen on EVERY request OR every response, applied uniformly.

  ---
  The real lesson — the middleware pattern

  The thing worth learning isn't "how to write a logger." It's:

  ▎ A middleware is the right place to put any logic that should run for every request or response, regardless of which view is involved.

  Once you know how to write one, you can solve dozens of problems with it: maintenance mode, auth, CORS, rate limits, tracing, compression.
  All of those are just __init__ + __call__ on a class — same shape as the logger, different content inside.

  My recommendation

  Two paths, your call:

  Path A — do the logger demo anyway (5 min)

  Just to internalize the pattern. The actual logger isn't valuable; the muscle memory of writing __init__(get_response) + __call__(request)
  is. Skip the print line if you want — leave it empty:

  class NoOpMiddleware:
      def __init__(self, get_response):
          self.get_response = get_response

      def __call__(self, request):
          # add stuff before view here
          response = self.get_response(request)
          # add stuff after view here
          return response

  Path B — write a more useful middleware

  Skip the logger, write a maintenance mode middleware instead. Demonstrably non-logging, and a real production-style example. ~10 min.

  from django.http import HttpResponse
  from django.conf import settings


  class MaintenanceModeMiddleware:
      def __init__(self, get_response):
          self.get_response = get_response

      def __call__(self, request):
          if getattr(settings, 'MAINTENANCE_MODE', False):
              if not request.path.startswith('/admin/'):
                  return HttpResponse('Site under maintenance. Back soon.', status=503)
          return self.get_response(request)

  Set MAINTENANCE_MODE = True in settings → every URL except /admin/ returns the maintenance page. Set it back to False → site comes alive
  again.

  This shows middleware short-circuiting the view — no view runs, response returned directly from middleware. Useful pattern, much more
  interesting demo.

  You understand the concept. We move on. You can write middleware whenever you actually need to.
