  What's literally in the search_vector column                                                                                                 
                                              
  Forget Django for a moment. Imagine a single post sitting in the DB:                                                                         
                                                                                                                                               
  title:  "Django ORM basics"                                                                                                                  
  body:   "I'm running through Django tutorials and learning a lot about ORMs."                                                                
                                                                                                                                               
  When you save the post, Django can ask PostgreSQL: "chew this text into a search-optimized form and store it in the search_vector column."
  PostgreSQL goes through these steps:

  Step 1 — lowercase
  "i'm running through django tutorials and learning a lot about orms."

  Step 2 — split into words (tokenize)
  ["i'm", "running", "through", "django", "tutorials", "and", "learning", "a", "lot", "about", "orms"]

  Step 3 — drop stopwords (common noise: "the", "a", "and", "through")
  ["running", "django", "tutorials", "learning", "lot", "orms"]

  Step 4 — stem each word to its root form
  "running"   → "run"
  "tutorials" → "tutori"
  "learning"  → "learn"
  "orms"      → "orm"

  Step 5 — store as a compact blob with positions
  'django':4 'learn':8 'lot':9 'orm':11 'run':2 'tutori':5

  That last line is literally what gets stored in the search_vector column for that post. Shorter than the body, lowercased, stemmed,
  deduplicated, indexed by position.

  So now you've got two columns holding two different views of the same content:

  ┌───────────────┬────────────────────────────────────────────┬────────────────────────┐
  │    Column     │               What it stores               │        Used by         │
  ├───────────────┼────────────────────────────────────────────┼────────────────────────┤
  │ body          │ Original human-readable text               │ Displayed on the page  │
  ├───────────────┼────────────────────────────────────────────┼────────────────────────┤
  │ search_vector │ Pre-chewed, stemmed, search-optimized blob │ Used by search queries │
  └───────────────┴────────────────────────────────────────────┴────────────────────────┘

  ---
  Why this is fast

  When a reader searches "running":
  1. PG stems "running" → "run"
  2. Looks for "run" in the search_vector blobs (with help from the GIN index — coming next)
  3. Matches found → returns the matching post rows

  It never reads the actual body text during the search. The search question is asked of the pre-chewed search_vector only. The original body
  just sits there untouched, ready to be displayed when the user clicks through.

  Two analogies if it helps:
  - Compiled bytecode. Your .py file is human-readable but slow to execute. Python compiles it to .pyc bytecode — not human-readable but fast
  for the interpreter. The body is the .py; the search_vector is the .pyc.
  - A hash. You don't compare two big files byte-by-byte; you compute hashes once and compare the hashes. Same reduction-for-fast-comparison
  pattern.

  ---
  Now your second question — why another class Meta?

  Excellent observation. Here's the answer:

  class Meta is per-model. Each model gets its own — they don't share.

  It's just a Django naming convention: "if you put a nested class called Meta inside a model, I'll read it for table-level configuration about
   that model." Every model that wants any table-level config gets its own Meta. They're independent inner classes that happen to share a name.

  Same way every class can have its own __init__ method — they all use the same name (__init__), but each one belongs to its own class and
  configures its own object. In your OOP practice:

  class Bank:
      def __init__(self, ...): ...    # Bank's __init__

  class Car:
      def __init__(self, ...): ...    # Car's __init__ — totally separate

  Two __init__ methods, both work, neither interferes with the other. Same here:

  class Category(models.Model):
      class Meta:
          verbose_name_plural = 'categories'    # Category's Meta

  class Post(models.Model):
      class Meta:
          ordering = ['-created_at']             # Post's Meta — totally separate
          indexes = [GinIndex(...)]

  Two Meta classes, both work, neither interferes. Each one configures its own model's table.

  What's going in Post's Meta

  Two things, both Post-specific:

  ┌──────────────────────────────────────────────┬─────────────────────────────────────────────────────────────────────────────────────────┐
  │                     Line                     │                                      What it does                                       │
  ├──────────────────────────────────────────────┼─────────────────────────────────────────────────────────────────────────────────────────┤
  │ ordering = ['-created_at']                   │ Default sort order: newest posts first. Without this, posts come back in arbitrary      │
  │                                              │ insertion order.                                                                        │
  ├──────────────────────────────────────────────┼─────────────────────────────────────────────────────────────────────────────────────────┤
  │ indexes =                                    │ The database index that makes search_vector lookups fast.                               │
  │ [GinIndex(fields=['search_vector'])]         │                                                                                         │
  └──────────────────────────────────────────────┴─────────────────────────────────────────────────────────────────────────────────────────┘

  Why doesn't Category need these? Because:
  - Category is tiny (~10 rows) — sort order doesn't matter much
  - Category has no search vector — no index needed

  Each Meta has only the configuration its own model actually needs. Category needed only verbose_name_plural. Post needs ordering + indexes.
  Different needs, different Metas.

  ---
 The GIN index for search_vector

  Last beat we said the search_vector column makes search possible, but the GIN index is what makes it fast. Quick framing:

  - Regular database indexes (the kind you've already met — slugs are auto-indexed) are B-tree indexes. They're optimized for one value per row
   — perfect for ids, slugs, emails.
  - A tsvector is different — it has many words inside one column value. A B-tree can't index that efficiently.
  - GIN = Generalized INverted Index. It's PostgreSQL's index type built for "many values per row" — exactly the shape of a tsvector.

  Without the GIN index: the search_vector column exists, but every search has to read every row to find matches. Slow.

  With the GIN index: searches jump straight to matching rows via the index. Milliseconds even at millions of rows. The GIN index is what
  unlocks the speed payoff we talked about in the Quora story.

  Rule of thumb: anywhere you have a SearchVectorField, you put a GinIndex on it. They go together.
