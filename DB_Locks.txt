● Why read-then-write opens the door

  Picture the Dhurandhar post's view count as a single sticky note on a fridge that says 1247.

  The naive Python way (the buggy way):

  Priya walks up to the fridge. She takes the note off, carries it to her desk, reads "1247", crosses it out, writes "1248", walks back, sticks
   it on the fridge.

  Riju does the same thing — but at the same instant. He grabs the note while Priya's already holding her own mental copy at her desk. He also
  reads "1247", writes "1248", walks back.

  Both stick "1248" on the fridge. The correct answer was 1249. One view evaporated.

  The structural mistake: the value left the database, lived in Python memory for a few milliseconds, then came back. During those few
  milliseconds, anyone else could be doing the same thing with a stale copy. That gap is the race.

  The fix — never let the value leave the database.

  Instead of "take the note, edit, put it back," you walk up to the fridge and say "add 1 to whatever's on this note." The fridge itself does
  the math. No copy on your desk, no gap, no race. If Priya and Riju both shout "add 1!" at the same time, the fridge processes them one after
  the other — 1247 → 1248 → 1249. No view lost.

  In Django, the way you say "do the math inside the DB" is F().

  ---
  The fix in two lines

  from django.db.models import F

  Post.objects.filter(pk=post.pk).update(views=F('views') + 1)

  Read that as: "go to the row with this pk, and set views = whatever views currently is + 1, all in one SQL statement." The value never enters
   Python. The DB does the increment atomically.

  The SQL it generates is literally:

  UPDATE posts_post SET views = views + 1 WHERE id = 5;

  One round trip. No read-modify-write split. Race-proof.

  def retrieve(self, request, *args, **kwargs):

  from django.db.models import F
  from rest_framework.response import Response

  Three things to know about what's happening:

  1. self.get_object() — the inherited helper that fetches the Post by pk from the URL and runs permission checks. You already use it
  implicitly via the inherited retrieve; now you're calling it yourself.
  2. .update(views=F('views') + 1) — the atomic increment. Doesn't touch instance in Python.

  back so the JSON response shows the bumped count.

  ---
  When F() is NOT enough

  F() works when the operation is "just add 1" — no thinking required, the DB can do it blindfolded.

  But sometimes you need to read the value, make a decision, then write. That decision has to happen in Python. And the moment the value leaves
   the DB to come to Python, the race condition is back.

  ---
  The seat-booking story

  Your favorite cinema is selling tickets for the Dhurandhar premiere. There is exactly one seat left.

  At 8:00:00.000 PM, two people both hit "Buy Ticket" — Priya and Riju.

  Priya's request:
  - Reads the seat counter → 1 seat left.
  - Code thinks: "1 > 0, so yes, sell it."
  - Charges Priya's card.
  - Writes counter back as 0.

  Riju's request (firing simultaneously):
  - Reads the seat counter → 1 seat left. (He read it before Priya wrote 0.)
  - Code thinks: "1 > 0, so yes, sell it."
  - Charges Riju's card.
  - Writes counter back as 0.

  Saturday night, both Priya and Riju show up with valid tickets for the same seat. One gets turned away. Theatre eats the refund. Manager
  apologizes. The internet gets a bad review.

  That's the bug. F() cannot fix it — because the line "if seats > 0, then sell" has to happen in Python. The DB doesn't know your business
  rule.

  ---
  What select_for_update does

  When Priya's request reads the seat counter, it puts a lock on that row. The lock says: "nobody else can touch this row until I'm done."

  Riju's request comes a millisecond later, tries to read the same row — and waits. Frozen. Not an error, just paused. He sits in line.

  Priya's code finishes: charges card, writes 0, releases the lock.

  NOW Riju's read finally happens. He reads 0. His code thinks: "0 > 0 is false — sorry, sold out." Riju sees a clean "Sold Out" message. No
  double-booking. No refund. No bad review.

  That's the whole idea of select_for_update: "give me this row AND make everyone else wait until I'm done with it."

● The code — same seat-booking story, in Django

  from django.db import transaction

  def buy_ticket(showing_id):
      with transaction.atomic():
          showing = Showing.objects.select_for_update().get(pk=showing_id)

          if showing.seats_left > 0:
              showing.seats_left -= 1
              showing.save()
              return "Sold!"
          else:
              return "Sold out."

  Read it top to bottom:

  1. with transaction.atomic(): — opens a transaction. Everything inside is one indivisible unit. When the block ends, the transaction commits
  (or rolls back if an exception fires).
  2. select_for_update() — when you fetch the row, also slap a lock on it. Any other request that tries to fetch this same row with
  select_for_update() will pause and wait for the lock to release.
  3. if showing.seats_left > 0: — the Python decision. Safe now, because nobody else can read this row until we finish.
  4. showing.save() — writes the new value back.
  5. End of with block — transaction commits, lock releases, Riju's waiting request wakes up.

  ---
  The one rule you must remember

  select_for_update() MUST be inside transaction.atomic(). Always. Without it, Django raises TransactionManagementError.

  Why? The lock is glued to the transaction. No transaction → nothing to glue the lock to → no lock. Django refuses to pretend.

  ---
  Why we used F() for views, not this

  For a plain counter (views + 1), there is no Python decision. The DB can do it alone. F() is one line, one SQL statement, zero locking
  overhead, zero blocking other requests. Right tool.

  For seat booking, inventory, balance transfers — anywhere the next value depends on a decision about the current value — reach for
  select_for_update().
