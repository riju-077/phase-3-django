  ---
  The book-index analogy (this is the one to remember):

  Open a 600-page programming textbook. You want to find the word "stemming".

  - Without an index: flip through every page, scanning for "stemming". Takes an hour. Every reader who wants it pays this cost.
  - With an index at the back: flip to the index, find "stemming → 247", jump to page 247. Three seconds. The author paid the index-building
  cost once. Every reader after that benefits forever.

  PostgreSQL's search_vector is the same trick.

  ---
  What "pre-chewing" actually does, every time you save a post:

  PostgreSQL takes the title + body, runs them through:

  1. Tokenize → split into words
  2. Lowercase → "RANVEER" becomes "ranveer"
  3. Stem → "movies" becomes "movi", "running" becomes "run"
  4. Drop stopwords → "the", "in", "a" thrown out
  5. Track positions → remember which word came where (so it can rank by closeness later)

  The output is a tidy little chewed-up summary like:

  'action':4 'dhurandhar':1 'japan':3 'ranveer':5 'releas':6 'singh':6 'spy':2

  That gets saved into the search_vector column on that row.

  When a reader searches "ranveer movies", PostgreSQL chews their query the same way → 'movi' 'ranveer' → and looks for those tokens inside the
   pre-chewed column. Pre-chewed vs pre-chewed = lightning fast.

  The GinIndex on top of that column is the cherry — it's a special index type built specifically for "find rows whose search_vector contains
  these tokens." Without it, PostgreSQL would still have to scan every row's pre-chewed column. With it, it jumps straight to the matching rows
   like the book index jumping to page 247.

  ---
  The fix — SearchRank. A function that scores each row by:
  - How many times the query words appear
  - How tightly packed they are
  - (Later, with weighted vectors) where they appear — title beats body

  Higher score → better match. Order by score descending → best first.

  ---
  ORM (try this in manage.py shell):

  from django.contrib.postgres.search import SearchQuery, SearchRank
  from posts.models import Post

  query = SearchQuery('ranveer')
  posts = (
      Post.objects
      .filter(search_vector=query)                          # only matches
      .annotate(rank=SearchRank('search_vector', query))    # add a rank score
      .order_by('-rank')                                    # best first
  )
  for p in posts:
      print(round(p.rank, 4), p.title)

  Expect output like:
  0.0608  RANVEER SINGH ACTION HEROES OF 2026
  0.0301  Dhruandhar in japan
  0.0150  Why Ranveer is reinventing himself
  0.0075  How spy thrillers are evolving

  The exact numbers are irrelevant — only the order matters.

         ts_rank(search_vector, to_tsquery('english', 'ranveer')) AS rank

  Beat — wire search into the API

  Now we plug all of this into /api/posts/?search=ranveer so the reader can actually use it.

  Where the wiring goes: PostViewSet in posts/api_views.py. Specifically, you override one method called get_queryset — it's the hook ViewSet
  calls to decide "which posts should this request see?" Currently you've set queryset = Post.objects.filter(published=True) as a class
  attribute (a fixed list). Override get_queryset and you can build it dynamically per request — read query params, filter, annotate, sort,
  return.

  What you'll add:

  from django.contrib.postgres.search import SearchQuery, SearchRank

  class PostViewSet(viewsets.ModelViewSet):
      serializer_class = PostSerializer
      permission_classes = [IsAuthenticatedOrReadOnly, IsAuthorOrReadOnly]

      def get_queryset(self):
          queryset = Post.objects.filter(published=True)

          search = self.request.query_params.get('search')
          if search:
              query = SearchQuery(search)
              queryset = (
                  queryset
                  .annotate(rank=SearchRank('search_vector', query))
                  .filter(rank__gte=0.001)
                  .order_by('-rank')
              )

          return queryset

      def perform_create(self, serializer):
          serializer.save(author=self.request.user)

  What changed:
  1. Removed the queryset = Post.objects.filter(...) class attribute — replaced by the method.
  2. Added get_queryset(self) — DRF calls this on every request to decide which rows are in scope.
  3. self.request.query_params.get('search') — pulls the ?search=... value from the URL. Returns None if absent.
  4. If a search term came in, annotate each row with a rank, filter to the relevant ones, order by rank descending. If no search term, return
  the plain published-posts list — falls back to default behavior.

  Why 0.001 not 0.1: CLAUDE.md uses 0.1 as a sane default, but with your tiny dataset rank values are tiny too. Lower threshold = nothing
  legitimate gets filtered out during dev. Tune up later when you have more data.

  Next beat — keep-fresh (the auto-update)

  Right now you've got a hole. Backfill filled the search_vector for the 5 existing posts. But what happens the moment akash creates post #6
  via the API or admin?

  Story: akash writes a brilliant new post titled "Why Aamir Khan's comeback matters." Saves it. A reader searches aamir two minutes later.
  Result: zero matches. The post exists, but its search_vector is NULL because nothing populated it on save. Backfill was a one-time chore — it
   didn't install any future-facing logic.

  So: every save (create or edit) needs to re-chew that post's text and update its search_vector. The clean Django way to do this is signals —
  Django's pub/sub system. You "subscribe" to a model's post_save event, and Django runs your function every time that model gets saved.

  The mental model:

  Post.save() ──► Django fires "post_save" signal
                            │
                            ▼
              Any subscribed function gets called
                            │
                            ▼
              (Our function: update search_vector for this post)

  Same pattern as JavaScript event listeners or any pub/sub system you've seen. Decouples the trigger (save) from the side-effect (update
  vector).

  ---
  The code lives in posts/signals.py (new file). Three things in it:

  from django.db.models.signals import post_save
  from django.dispatch import receiver
  from django.contrib.postgres.search import SearchVector
  from .models import Post


  @receiver(post_save, sender=Post)
  def update_search_vector(sender, instance, **kwargs):
      Post.objects.filter(pk=instance.pk).update(
          search_vector=SearchVector('title', 'body')
      )

  Then wire it up in posts/apps.py so Django actually loads the signals at startup. Add this ready method to your PostsConfig class:

  class PostsConfig(AppConfig):
      default_auto_field = 'django.db.models.BigAutoField'
      name = 'posts'

      def ready(self):
          from . import signals    # noqa: F401  — registers the signal handler

  (The default_auto_field and name lines should already be there — only ready is new.)

  ---
  Why Post.objects.filter(pk=...).update(...) and NOT instance.search_vector = ...; instance.save():

  If you call instance.save() inside a post_save handler, you trigger another post_save, which calls the handler again, which calls save()
  again — infinite loop, server crash. Using .update() writes directly to the DB and bypasses the signal. Same trick as the backfill —
  .update() doesn't fire save() events.

  This is mistake-magnet territory. Worth the 10 seconds to internalize.
