 Q1: What is python manage.py shell?                                                                                                          
                                                                                                                                               
  Not a UI for end users. End users never see this. It's a developer's private command line for talking to your Django app and database.       
                                                            
  What it actually is

  Two parts:
  - python manage.py — runs Django's management tool (the same one you've been using for migrate, runserver, startapp).
  - shell — opens an interactive Python prompt, but with Django already booted up (settings loaded, models imported, DB connection ready).

  You've used python in a terminal before, right? You get the >>> prompt and can type Python line by line. That's a REPL — Read, Evaluate,
  Print, Loop. Type code, press Enter, see result. python manage.py shell is the same REPL, but with Django pre-loaded so you can talk to your
  models and database immediately.

  What you actually use it for

  - Sanity-check your models. "Did the migration work? Let me try creating a Category."
  - Inspect data. "How many posts does akash have? akash.posts.count()"
  - Debug. "Why is this query returning the wrong rows? Let me run it interactively."
  - One-off data fixes. "I need to fix one row in production. SSH in, open the shell, fix it, exit."
  - Learning. Right now, while learning Django, the shell is your sandbox. Every concept you learn — try it in the shell first.

  Better analogy than "user UI"

  Think of it as the developer's back door to your running application. Like opening Chrome DevTools' console — except instead of poking at the
   frontend, you're poking at the backend. End users never get this; only the developer does.

  Or another framing: it's a Python REPL with Django auto-imported. That's the most literal description.

  How to run it

  uv run python manage.py shell

  (Same uv run prefix you've been using to activate the venv automatically.)

  You'll get >>> and can type things like:
  >>> from posts.models import Category
  >>> Category.objects.all()

  It talks to your real blog_db. So creating a row in the shell creates a real row in PostgreSQL. Treat it as production-grade — anything you
  do here is real.

  Q2: What does "Python's memory" mean?

  You're right that disk = your laptop's SSD/HDD. Memory is the other half of the storage story.

  Two storage layers in any computer

  ┌─────────────┬────────────────────────────────┬────────────────────────────────────────────────────────────┐
  │             │          RAM (memory)          │                       Disk (SSD/HDD)                       │
  ├─────────────┼────────────────────────────────┼────────────────────────────────────────────────────────────┤
  │ Speed       │ Very fast (nanoseconds)        │ Slow (milliseconds)                                        │
  ├─────────────┼────────────────────────────────┼────────────────────────────────────────────────────────────┤
  │ Size        │ Small (your 16 GB or so)       │ Large (your 512 GB or 1 TB)                                │
  ├─────────────┼────────────────────────────────┼────────────────────────────────────────────────────────────┤
  │ Persistence │ Lost when computer turns off   │ Survives shutdown                                          │
  ├─────────────┼────────────────────────────────┼────────────────────────────────────────────────────────────┤
  │ Cost per GB │ Expensive                      │ Cheap                                                      │
  ├─────────────┼────────────────────────────────┼────────────────────────────────────────────────────────────┤
  │ Used for    │ Programs while they're running │ Files, databases, anything that has to outlive the program │
  └─────────────┴────────────────────────────────┴────────────────────────────────────────────────────────────┘

  How this applies to your code

  When you run python script.py:

  1. Python reads the script from disk into memory.
  2. Every variable, every object, every class you create lives in memory.
  3. When the script ends, that memory is freed. Everything in it is gone.

  Concretely with your Bank example:

  sbi = Bank("SBI", "SBI0001")    # sbi exists in RAM
  icici = Bank("ICICI", "ICIC0001") # icici exists in RAM

  # Script ends — Python exits — RAM is freed.
  # sbi and icici no longer exist anywhere.

  If you wanted sbi to survive past the script exit, you'd have to save it to disk — into a file, a database, anywhere persistent.

  How this maps to Django

  ┌────────────────────────┬──────────────────────────────────────────────────────────────────────────────────────┐
  │     Where it lives     │                                      What it is                                      │
  ├────────────────────────┼──────────────────────────────────────────────────────────────────────────────────────┤
  │ Disk (PostgreSQL)      │ Your tables — posts_post, auth_user, etc. The rows.                                  │
  ├────────────────────────┼──────────────────────────────────────────────────────────────────────────────────────┤
  │ Memory (Python/Django) │ Your model classes (Post, Category), the running server, every request being handled │
  └────────────────────────┴──────────────────────────────────────────────────────────────────────────────────────┘

  When a request comes in to view post #1:

  1. Django queries PostgreSQL: SELECT * FROM posts_post WHERE id=1 → reads a row from disk.
  2. Django constructs a Post object in memory with that row's data.
  3. Your view function uses the in-memory object: post.title, post.author, etc.
  4. Django renders the response and sends it back.
  5. The in-memory Post object gets garbage-collected — gone from memory.
  6. The row in PostgreSQL is untouched. Still on disk.

  So when I said "Django attaches a .posts attribute to the User class in memory," I meant: while the Django server is running, the User class
  object sits in RAM, and Django attaches that attribute to it. If you stop the server, the in-memory User class disappears. When you start it
  again, Django re-loads everything and re-attaches the attribute. The PostgreSQL auth_user table sat untouched on disk the whole time.

  Why this split exists

  Memory is fast but volatile. Disk is slow but durable. Servers exploit both:
  - Working data lives in memory (fast access).
  - Persistent state lives on disk (survives crashes, restarts, deployments).
  - The database (PostgreSQL) is the bridge: it lives on disk but is fast enough to be useful.

  When Django says "saves to the database" — it means the data went from memory to disk. When Django says "queries the database" — it means
  data came from disk into memory. The database is just a smart, structured place on disk.

  Tying back to your project

  Right now:
  - Your models.py lives on disk in D:\DATA_S\django\blog\posts\models.py.
  - When Django runs, it reads that file into memory and creates Python class objects (Category, Post).
  - The actual rows of categories and posts (none yet) live on disk in PostgreSQL's data files.
  - When a request fetches a post, Django pulls the row off disk, creates an in-memory Post object, hands it to your view function, then frees
  it.

  This split — Python objects in memory, table rows on disk — is the entire mental model. Once it's solid, the rest of Django's behavior makes
  sense.

Yes — that's exactly the right shape. You've nailed the core split:                                                                          
                                         
  - Class definitions → live in .py files (models.py).                                                                                         
  - Instance creation / testing / exploration → happens elsewhere, including the shell.
                                                                                                                                               
  Same pattern as your Bank example, just split across two places instead of one file.

  One small refinement

  The shell is one developer tool — not the only way usage code gets triggered. In a real Django app, instance creation happens through several
   paths:

  ┌─────────────────────┬─────────────────────────────────────────────────────────┬────────────────────────────────────────────────┐
  │        Path         │                      Triggered by                       │                  Who uses it                   │
  ├─────────────────────┼─────────────────────────────────────────────────────────┼────────────────────────────────────────────────┤
  │ The shell           │ You typing in the terminal                              │ Developer (you, debugging)                     │
  ├─────────────────────┼─────────────────────────────────────────────────────────┼────────────────────────────────────────────────┤
  │ The Django admin    │ A staff user clicking buttons                           │ Site admins (akash logging in to manage posts) │
  ├─────────────────────┼─────────────────────────────────────────────────────────┼────────────────────────────────────────────────┤
  │ View functions      │ A real end user submitting a form                       │ Anyone visiting the website                    │
  ├─────────────────────┼─────────────────────────────────────────────────────────┼────────────────────────────────────────────────┤
  │ API endpoints (DRF) │ A mobile app or React frontend hitting POST /api/posts/ │ External clients                               │
  ├─────────────────────┼─────────────────────────────────────────────────────────┼────────────────────────────────────────────────┤
  │ Management commands │ You running python manage.py somecommand                │ Developer (scheduled jobs, data migrations)    │
  ├─────────────────────┼─────────────────────────────────────────────────────────┼────────────────────────────────────────────────┤
  │ Tests               │ You running pytest                                      │ Automated CI                                   │
  └─────────────────────┴─────────────────────────────────────────────────────────┴────────────────────────────────────────────────┘

  All six of these end up doing the same thing under the hood: Post(title=..., author=...).save() — your sbi = Bank(...) moment, just dressed
  up with different triggers.

  So a more accurate framing:

  ▎ "Django doesn't have one developer UI. It has many entry points. The shell is one of them — the rawest one, where I write Python directly.
  ▎ The admin, the views, the API are other entry points dressed up for non-developers."

  The shell is your sandbox to simulate what those other entry points do, without needing a browser or a frontend yet.
